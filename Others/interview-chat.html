When you use WebClient: No thread babysits. The system sends the request and tells the OS: "Wake me up when the data arrives." The thread is immediately released to do other work. You could handle those 500 requests with just 4 or 8 threads.

This is the fundamental principle of Non-Blocking I/O. Unlike traditional blocking I/O (RestTemplate), where each thread "sleeps" until data arrives, WebClient uses an Event Loop model (powered by Netty).

Key Concept

  • Blocking (RestTemplate): 500 requests = 500 threads sitting idle, doing nothing but waiting.
  • Non-Blocking (WebClient): 500 requests = 4-8 threads juggling all requests. No thread waits.
💡 Additional Info: The "Event Loop" is similar to how Node.js works. A single loop constantly checks: "Is any data ready?" When data arrives, it picks it up and processes it. This is why reactive systems can handle massive concurrency with minimal resources.
The call is handled by a thread. Then what is happening? If the network is reached, what will happen? When network reaches back, what happens if that particular thread is not available?

Think of it less like a dedicated waiter standing at your table, and more like a high-tech kitchen where the staff only touches a dish when there is an actual action to perform.

1 The Hand-off: "Registered, Not Waiting"

When you make a call with WebClient, the request is handled by a thread from an Event Loop group (usually powered by Netty).

  • The Action: The thread sends the request to the Network Interface Card (NIC).
  • The Registration: Instead of staying on the line, the thread registers a "callback" or a "selector" with the Operating System (using mechanisms like epoll on Linux or kqueue on macOS).
  • The Release: The thread says, "I'm done for now," and immediately goes back to the pool to handle other incoming HTTP requests or calculate logic.

2 At the Network Level

While the data is traveling across the internet, no thread in your application is doing anything for this specific request. The CPU is effectively at 0% usage for this task. The "waiting" is happening at the hardware level (the NIC) and the OS Kernel level.

3 The "Wake Up" (The Arrival)

When the response data finally hits your network card:

  • The OS Kernel receives the packets.
  • The Kernel sees that a specific "Socket" has data ready.
  • The Kernel triggers an event (a signal) to your application's Event Loop.

4 What if that original thread is busy?

This is the "aha!" moment: It doesn't matter.

In a non-blocking system, any available thread in the Event Loop pool can pick up the response.

  • The Task is an Event: The "arrival of data" is just a new task placed in a queue.
  • The Thread Pool: The Event Loop (usually a very small number of threads, like the number of CPU cores) is constantly spinning. As soon as one is free, it picks up your data and starts processing.
Key Insight: If "Thread A" (who started the request) is busy calculating a math problem for another user, "Thread B" will simply pick up your response and finish the job. They are all "equal" in the eyes of the Event Loop.

5 How does it remember what to do?

If a different thread picks up the work, you might wonder: "How does it know where we left off?"

This is handled by State. When the request was first sent, WebClient created a small object (a "continuation" or "callback chain") that contains:

  • The instructions on what to do next (e.g., map, flatMap, subscribe).
  • The context (security headers, user IDs, etc.).

This object lives in the Heap memory, not on the Thread Stack. Because it's in the Heap, any thread in the pool can grab that object, look at the instructions, and execute them.

It looks like you've made a great first step by parallelizing your calls using CompletableFuture. However, you are currently caught in the "Async Paradox." How do we fix this?

1 The "Fake Async" Trap (The .join() problem)

In your getStaticData method, you have this line:

CompletableFuture.allOf(tenantDataFuture, localeFuture).join(); // THIS IS BLOCKING

By calling .join(), you are telling the Spring Boot request thread: "Don't do anything else. Sit here and wait until these two tasks are done." While the tasks run in parallel, you are still tying up a worker thread for the entire duration of the I/O. In a high-traffic environment, this leads to Thread Starvation.

⚠️ The Fix: Instead of returning LandingPageStaticDataResponse, your service should return CompletableFuture<LandingPageStaticDataResponse>.

2 Stop Wrapping Blocking Calls

Currently, you are doing this:

CompletableFuture.supplyAsync(() -> landingPageTenantDao.findLandingPageData(...))

This is "Manual Async." You are taking a blocking DAO call and forcing it into a separate thread pool (dynamoDbExecutor). This is better than serial execution, but it's inefficient because you're just managing a bunch of "waiting" threads.

✅ The Fix: Use the AWS SDK v2 Async Client. If you switch your landingPageTenantDao to use the DynamoDbAsyncClient, the code becomes much cleaner and uses zero extra threads to wait for the database.

What your code should look like:

public CompletableFuture<LandingPageStaticDataResponse> getStaticData(
        String languageCode, String category, Boolean status) {
    String tenantCode = TenantUtil.getTenantCode();

    // No supplyAsync needed! These return Futures natively.
    CompletableFuture<LandingPageTenantData> tenantDataFuture =
        landingPageTenantDao.findLandingPageDataAsync(tenantCode, category, status);
    CompletableFuture<List<LocaleRequestDTO>> localeFuture =
        localeDataService.getLocaleDataByLanguageCodeAsync(languageCode);

    // Chain the results together without EVER calling .join()
    return CompletableFuture.allOf(tenantDataFuture, localeFuture)
        .thenApply(v -> {
            LandingPageTenantData tenantData = tenantDataFuture.join(); // Safe here, they are finished
            return LandingPageStaticDataResponse.builder()
                .popularLink(toPopularLinksResponse(tenantData.getPopularLinks()))
                // ... rest of mapping
                .build();
        });
}

Will it create a "drastic change"?

Yes, but with a major catch. If you just move the calls to the backend but execute them one after another, you'll save on network "trips," but the total time might still be high.

1 Why it helps (The Good News)

  • Reduced Round-Trip Time (RTT): Latency between a user's phone/browser and your server is usually high (~100ms). Latency between backend services is tiny (<5ms). Moving logic to the backend cuts out the "long distance" travel.
  • Smaller Payload: Instead of the frontend receiving 10 massive JSON objects and only using two fields from each, your "aggregator" can strip out the junk and send back exactly what the frontend needs.
  • Less Overhead: You only do one TLS handshake and one set of headers/authentication instead of dozens.

2 The "RestTemplate" Trap

By default, RestTemplate is synchronous (blocking). If your new service calls Service A, waits, then calls Service B, then waits, the user is still stuck waiting for the sum of all response times.

✅ How to optimize: Use CompletableFuture (if sticking with Java/Spring) to fire off all requests at once. The total wait time will then be the time of the slowest single service, not the sum of all of them.

If I use CompletableFuture, what are the trade-offs?

Switching from sequential to CompletableFuture is like moving from a single-lane road to a multi-lane highway. It's much faster, but the risk of a "traffic jam" or a "crash" becomes more complex to manage.

1 The "Common Pool" Trap (Resource Exhaustion)

By default, CompletableFuture uses the ForkJoinPool.commonPool().

  • The Risk: This pool is shared across your entire JVM. If your API aggregation logic gets hit with high traffic and eats up all threads in the common pool, it can starve other parts of your application.
  • The Fix: Always define a Custom Executor (a dedicated Thread Pool).

2 Loss of Context (The "Who Am I?" Problem)

Many frameworks use ThreadLocal variables to store data like:

  • Spring Security Context: The current logged-in user.
  • MDC/Logging: The Trace ID used to follow a request through logs.
  • Transaction Context: Database transaction state.
⚠️ The Trade-off: When you jump to a new thread via CompletableFuture, that ThreadLocal data does not follow you. Your logs might show a blank "User ID," or your security checks might fail.

3 "Hell" of Exception Handling

In a synchronous world, you just use try-catch. In an asynchronous world, if one of your 10 API calls fails:

  • You must decide: if Call #4 fails, do we fail the whole request? Or return "null" for that field?
  • You must use methods like .handle(), .exceptionally(), or .whenComplete().

4 The "Slowest Link" Bottleneck

Even with 100 threads, your total response time is governed by the slowest single API.

  • The Risk: If 9 APIs respond in 50ms but the 10th takes 5 seconds, your "fast" aggregator still takes 5 seconds.
  • The Fix: Implement Timeouts on every CompletableFuture.

Loss of Context (The "Who Am I?" Problem) — couldn't understand. Explain with example.

Imagine your backend is like a high-end restaurant.

When a request comes in, a Waitstaff (The Main Thread) is assigned to that table. This waiter carries a "notepad" (the ThreadLocal) where they've written down important things: the Customer's Name, the Table Number, and the Order ID.

When you use CompletableFuture, it's like the waiter hiring a Runner (A Worker Thread) from the kitchen to go fetch the appetizer.

The "Who Am I?" Scenario

  • The Waitstaff (Thread A) knows the Customer is "Alice" and the Trace ID is REQ-123.
  • The Waitstaff tells the Runner (Thread B): "Go fetch the salad."
  • The Runner (Thread B) runs to the salad station. But here is the problem: The Runner didn't take the Waitstaff's notepad.

A Real Code Example

// We are in the Main Request Thread (Thread A)
log.info("Processing request for user: " +
    SecurityContextHolder.getContext().getAuthentication().getName());
// Output: "Processing request for user: Alice"

CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    // We are now in a Background Thread (Thread B)

    // 1. LOGGING FAIL:
    log.info("Fetching data...");
    // Output: "Fetching data..." (The Trace ID is MISSING from the logs!)

    // 2. SECURITY FAIL:
    String user = SecurityContextHolder.getContext()
        .getAuthentication().getName();
    // CRASH! NullPointerException. Thread B has no idea who "Alice" is.

    return "Data";
}, customExecutor);

The Risks in Detail

  • MDC (Logging): If you don't propagate the context, your logs will be a mess. You'll see a request start with TraceID: 123, but the actual work will have no ID.
  • Spring Security: Your CompletableFuture will fail with a 401 Unauthorized because it thinks an "Anonymous User" is trying to make the call.
  • Transactions (@Transactional): Transactions are tied to the thread. If Thread A starts a transaction and Thread B tries to save data, Thread B is not part of Alice's transaction. If Thread A rolls back, Thread B's work might have already been committed.
When the context is lost, what is supposed to happen then?

When the context is lost, your application doesn't just "slow down"—it starts failing in confusing ways or becoming impossible to debug.

1 The Security "Access Denied" Failure

The new thread tries to execute an API call. It looks for the user's "Security Badge" in its ThreadLocal memory. It finds nothing.

  • You get a NullPointerException (if your code assumes a user is logged in).
  • Or, Spring throws an AccessDeniedException or a 401 Unauthorized, even though the user is actually logged in.

2 The "Invisible" Logs (MDC)

Your main thread logs: [ID: 12345] - Starting Request. Then the CompletableFuture starts. The background thread's logs: [ID: ] - Fetching User Profile.

When a bug happens in production, you search your logs for ID: 12345. You will only see the start and end. All the "meat" of what happened inside the parallel threads will be invisible to your search.

3 API Token Disappearance

If your RestTemplate/Feign client is configured to grab a JWT token from the current request, the interceptor looks for the RequestContext. Since it's a new thread, the RequestContext is null. The outgoing call is sent without an Authorization header. Your other backend services will reject the call with a 401 Unauthorized.

4 Database Transaction Breakage

If your main method is @Transactional and you start a CompletableFuture that writes to the database, that background work is not part of the same transaction.

  • If the main request fails and rolls back, the background thread's work will not roll back.
  • You end up with "zombie data"—part saved, the rest lost.

How to solve this (The "Spring Way" — TaskDecorator)

public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        // 1. Grab the "notepad" from the Main Thread
        Map<String, String> contextMap = MDC.getCopyOfContextMap();
        SecurityContext securityContext = SecurityContextHolder.getContext();

        return () -> {
            try {
                // 2. Put the "notepad" into the Background Thread
                if (contextMap != null) MDC.setContextMap(contextMap);
                SecurityContextHolder.setContext(securityContext);

                runnable.run();
            } finally {
                // 3. Clean up when finished
                MDC.clear();
                SecurityContextHolder.clearContext();
            }
        };
    }
}
Who is ThreadLocal?

ThreadLocal isn't a "who"—it is a "where."

Think of ThreadLocal as a private locker inside a thread. It is a special way to store data so that it is only accessible by the specific thread that put it there.

The Analogy: "Shared Fridge" vs. "Personal Lunchbox"

  • Static/Global Variables (The Shared Fridge): If you put a sandwich in a shared office fridge, anyone can eat it or change it. This leads to "Race Conditions."
  • ThreadLocal (The Personal Lunchbox): Every employee brings their own lunchbox. Even if everyone is eating "a sandwich," you only have access to your sandwich.

The 3 Most Common Contents of a ThreadLocal Locker

  1. Security Context: "Who is the user currently making this request?" (Spring Security)
  2. Transaction Status: "Is there a database transaction currently open for this thread?"
  3. Trace ID: "What is the unique ID for this specific request so I can track it in the logs?" (MDC)

Instead of writing: userService.doSomething(user, token, traceId, transactionId);

You just write: userService.doSomething(); — Inside that method, you ask the ThreadLocal for the values.

The "Memory Leak" Danger

⚠️ Critical: Because threads in backend services (like Tomcat) are reused (Thread Pooling), the thread doesn't "die" after a request. If you put data into a ThreadLocal and don't clean it up, the next request that uses that same thread will "inherit" the old data. User A finishes → User B starts on the same thread → System thinks User B is User A.

This is why you almost always see ThreadLocal used with a try-finally block to ensure threadLocal.remove() is called.

Why this breaks your CompletableFuture

  • Thread A (Main): Has "User: Alice" in its locker.
  • Thread B (CompletableFuture): Is a totally different thread. It has its own lockers, but they are all empty.
CompletableFuture is what I used. So when I called other service, as response it is giving null for particular fields.

This is exactly what happens when the "Who Am I?" problem strikes. The most common reason for those specific null values when using CompletableFuture is a Missing Authorization Header.

The "Silent Failure" Scenario

  1. The Interceptor Fails: You probably have a RestTemplate interceptor configured to grab the JWT token from the current request.
  2. ThreadLocal is Empty: Because you are in a CompletableFuture thread, that interceptor asks the ThreadLocal for the token. The ThreadLocal says: "I don't have a token."
  3. The Request is Sent "Naked": Your aggregator service calls the downstream service without the security token.
  4. Downstream Service Logic: The downstream service sees no token. Instead of crashing (401), it might return a "Public Version" where sensitive fields are simply null.

How to Verify This (The Debug Test)

CompletableFuture.supplyAsync(() -> {
    // TEST 1: Check Security Context
    System.out.println("User in Thread: " +
        SecurityContextHolder.getContext().getAuthentication());

    // TEST 2: Check Request Headers (if using Spring Web)
    System.out.println("Request Attributes: " +
        RequestContextHolder.getRequestAttributes());

    return otherService.getData();
}, myExecutor);

If those print null, you have found your culprit.

Other Common Causes for null in CompletableFuture

  • The "Swallowed" Exception: If you have .exceptionally(ex -> { return null; }) — if the downstream timed out, your code returns null.
  • Jackson Mapping (Naming Mismatch): snake_case vs camelCase mapping issues.
  • Race Conditions: Trying to access the result before CompletableFuture finished.

The Immediate Fix

// 1. Capture context in the MAIN thread
SecurityContext context = SecurityContextHolder.getContext();

CompletableFuture.supplyAsync(() -> {
    try {
        // 2. Set context in the NEW thread
        SecurityContextHolder.setContext(context);
        return restTemplate.getForObject(url, MyClass.class);
    } finally {
        // 3. Always clear it!
        SecurityContextHolder.clearContext();
    }
}, myExecutor);
How to solve the issue "Who Am I"? ThreadLocal purpose?

To solve the "Who Am I" problem, you need to build a bridge between your main thread and your background threads.

Option A: The Manual Hand-off (Quick fixes)

// 1. Capture the "Who Am I" info in the MAIN thread
SecurityContext context = SecurityContextHolder.getContext();
Map<String, String> mdcContext = MDC.getCopyOfContextMap();

CompletableFuture.supplyAsync(() -> {
    try {
        // 2. Set the "Who Am I" info in the NEW thread
        SecurityContextHolder.setContext(context);
        if (mdcContext != null) MDC.setContextMap(mdcContext);

        // Now your API call will have the User and the Trace ID!
        return restTemplate.getForObject(url, MyClass.class);
    } finally {
        // 3. IMPORTANT: Clean up so the thread is fresh for the next request
        SecurityContextHolder.clearContext();
        MDC.clear();
    }
}, myExecutor);

Option B: The "Spring Way" (TaskDecorator) — Recommended

Define the Decorator:

public class ContextCopyingDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        SecurityContext context = SecurityContextHolder.getContext();
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        return () -> {
            try {
                SecurityContextHolder.setContext(context);
                if (mdc != null) MDC.setContextMap(mdc);
                runnable.run();
            } finally {
                SecurityContextHolder.clearContext();
                MDC.clear();
            }
        };
    }
}

Apply it to your Executor:

@Bean
public Executor myExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setTaskDecorator(new ContextCopyingDecorator()); // The magic line
    executor.initialize();
    return executor;
}

Why CompletableFuture is asking for that ThreadLocal? For normal request it is not using.

The reason "normal" requests don't ask you for this is because of the Thread-per-Request model used by servers like Tomcat.

1 The "Normal" Request (The Straight Line)

When a request hits your server, Spring assigns one single thread to handle it from start to finish. Whether you are in the Controller, Service, or Repository, you are in the same thread, so the "pocket" (ThreadLocal) is always accessible.

Spring automatically fills that pocket at the very beginning of the request and cleans it at the end. You never see it happening.

2 The CompletableFuture (The Branch)

The moment you use CompletableFuture.supplyAsync, you are explicitly telling Java: "Stop using this thread and go do this work on a DIFFERENT thread."

  • The Wall: Threads are designed to be isolated. Thread A cannot see inside the "pockets" (ThreadLocal) of Thread B. This is a security feature of the JVM.
  • The Disconnect: Spring's "magic" only knows about the original request thread. It has no idea you've spawned a new sub-thread.

Why doesn't Java just copy it automatically?

  • Performance: Copying data every time a thread is created would make the system slow.
  • Safety: If a background thread modified a "User" object while the main thread was also using it, you'd get unpredictable bugs (Race Conditions).
  • Cleanliness: If 10 sub-threads inherit data and one forgets to clear it, you get "Memory Leaks."
From frontend if hitting a request, ThreadLocal holds the data and then when we use CompletableFuture, that call is handed over to other separate threads. Then what happens to ThreadLocal? Each one has separate ThreadLocals?

You've hit the nail on the head. Each Thread object in Java has a hidden internal field called threadLocals. This is essentially a specialized Map (ThreadLocalMap) that belongs exclusively to that specific thread.

The Lifecycle of the "Hand-off"

  1. Thread A (The Request Thread): Spring populates Thread A's ThreadLocalMap with your User ID, JWT, and Trace ID.
  2. The Trigger: You call CompletableFuture.supplyAsync().
  3. The New Player: Java grabs Thread B from a Thread Pool (like ForkJoinPool or your custom executor).
  4. The Isolation: Thread B has its own, entirely separate ThreadLocalMap.
    • It does not inherit anything from Thread A.
    • It starts with an empty map (or worse, "dirty" data left over from the last task that used Thread B).

"Wait, what about InheritableThreadLocal?"

⚠️ Why you should NOT use it here: InheritableThreadLocal only works if Thread A literally creates Thread B right then. In modern backend apps, we use Thread Pools. Thread B already exists; it's just sitting in a pool waiting for work. Since Thread A isn't "parenting" Thread B, the inheritance never happens.

So what is the best approach? GraphQL and?

The "best" approach isn't just one tool—it's a combination of a smart Interface (how the frontend talks to you) and a powerful Engine (how you talk to your services).

1 The Interface: GraphQL Federation

Define a "Schema" for all your data. The frontend sends one single query. The GraphQL engine acts as the "Traffic Controller"—it knows which services have which data and fetches them all in one go.

2 The Engine: Spring WebClient (Non-Blocking)

WebFlux doesn't rely on ThreadLocal. It uses Reactor Context. It's built specifically to carry security and logging data across different threads automatically.

Then what is reactive programming? Spring Boot WebFlux?

If RestTemplate is a walkie-talkie (one person talks, the other listens, and nobody else can use the line), then Spring Boot WebFlux is like a WhatsApp group chat. You send a message, put your phone in your pocket, and go about your day until you get a notification.

1 The Core Concept: The "Event Loop"

In a normal Spring Boot app (MVC): 200 users = 200 threads.
In WebFlux (Reactive): You only need a handful of threads (usually equal to your CPU cores).

2 The Vocabulary: Mono and Flux

  • Mono<T>: A promise for one (or zero) item. (e.g., fetching a user by ID)
  • Flux<T>: A promise for a stream of items (0 to N). (e.g., a real-time feed of stock prices)

3 Why it's the "Secret Weapon" for your Lag

  • Native Aggregation: "Zip" 10 different API calls (Monos) together. WebFlux handles the parallelism automatically.
  • Context Propagation: Uses Reactor Context instead of ThreadLocal. The context is attached to the stream, not the thread.
  • Backpressure: If services send data faster than your frontend can handle, WebFlux can tell them to "slow down."

Then what about WebClient? Deep dive.

If RestTemplate is the old, reliable hammer, WebClient is the high-powered nail gun. It was introduced in Spring 5 as the official successor to RestTemplate.

1 It is Non-Blocking (The End of Waiting)

With RestTemplate, a thread waits at a counter for coffee. With WebClient, the thread orders, gets a pager, and immediately helps another customer.

2 Native Parallelism (No more CompletableFuture)

public Mono<CombinedData> getAggregatedData(String id) {
    Mono<User> userMono = webClient.get()
        .uri("/users/{id}", id)
        .retrieve().bodyToMono(User.class);

    Mono<Course> courseMono = webClient.get()
        .uri("/courses/{id}", id)
        .retrieve().bodyToMono(Course.class);

    Mono<Progress> progressMono = webClient.get()
        .uri("/progress/{id}", id)
        .retrieve().bodyToMono(Progress.class);

    // This fires all three requests IN PARALLEL automatically
    return Mono.zip(userMono, courseMono, progressMono)
        .map(tuple -> new CombinedData(
            tuple.getT1(), tuple.getT2(), tuple.getT3()));
}

3 It Solves "Who Am I" (Reactor Context)

WebClient doesn't use ThreadLocal. It uses Reactor Context. The Context is a "backpack" physically attached to the data stream itself. No matter how many times the data jumps threads, the "backpack" goes with it.

If we use WebClient, then why Micrometer Context Propagation? Also, why does the background thread need to know "Who Am I" for making that call? Just make the call and bring the data. Also after getting the data, will it directly hand over to CPU?

Part 1: Why does the background thread need to know "Who Am I"?

In a professional Enterprise/LMS system, the background thread needs "Who Am I" for two critical reasons:

  • The Security Badge (Authorization): Most backend services are protected. Thread B needs to attach a JWT Token to the header. Without it, the downstream service returns a 401 Unauthorized or null data.
  • The Breadcrumb Trail (Tracing): If the API call fails, you need to trace it in your logs. Without the Trace ID, the logs from Thread B will be disconnected from the main request.

Part 2: Why Micrometer if we use WebClient?

Your incoming request starts in a traditional Spring MVC thread which does use ThreadLocal. WebClient is reactive and doesn't use ThreadLocal. Micrometer Context Propagation is the "translator". It takes the data out of the traditional "ThreadLocal pocket" and puts it into the WebClient's "Reactive Backpack" (Reactor Context).

⚠️ "Stuck" means: Thread A puts the "Security Token" in its private safe. Thread A sends a message to Thread B: "Go call the Course Service." Thread B looks for a safe in its own room. Its safe is empty. It cannot walk into Thread A's room to open that safe.

Part 3: Does it "hand over to CPU" after getting data?

  1. The Network: Data arrives at your Network Card.
  2. The Kernel: The Operating System receives it.
  3. The Thread: In an Async/WebClient world, the OS sends an "Interrupt" (a notification). A thread from the pool wakes up, grabs the data from memory, and the CPU then processes it.
The "brilliance" of Async: The CPU only works when there is actually data to process, instead of sitting idle while the network is busy.

CompletableFuture vs. WebClient — The Core Difference

When you use CompletableFuture with RestTemplate:

  • The Main Thread is free (it's not babysitting).
  • But the Background Thread IS babysitting. It sits there doing nothing while waiting for the network response.
  • 100 students × 5 services = 500 threads sitting idle. Each takes ~1MB RAM.

When you use WebClient:

  • No thread babysits. The system sends the request and tells the OS: "Wake me up when the data arrives."
  • You could handle those 500 requests with just 4 or 8 threads.
